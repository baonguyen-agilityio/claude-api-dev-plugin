# Project profile

Every repo that uses this kit carries a short profile as a marked block in its `CLAUDE.md`. Claude Code loads `CLAUDE.md` into every session, so the profile is in context before any skill runs; each skill follows it where it differs from the skill's own defaults. `/backend-dev:kit-setup` drafts the block from the repo; a lead reviews and commits it. A value nobody could establish stays as `?: <question for the lead>`, never a guess.

## The block

```markdown
<!-- backend-dev:profile:start -->
## Backend profile
**Kit:** backend-dev plugin. Use its skills for backend work (system-design, data-model, api-contract, implement, review-and-secure, live-verify, delivery, incident); a ticket goes `/backend-dev:ticket <id>` → `plan` → `build` → `prove` → `settle`, `/backend-dev:review <MR>` reviews a teammate's MR, `/backend-dev:onboard` maps the project.
**Repo:** <single app | monorepo: apps in <path>, shared code in <path>>; API app: <path>
**Commands:** install `<cmd>`; dev `<cmd>`; gates `<lint or typecheck>` && `<test>` && `<build or dry-run>`; deploy `<cmd per env>` (only with the user)
**Layering:** <route → controller → service → repository>; a new endpoint touches <files>
**Errors:** <how a failure is raised and where it becomes a status>; <what counts as a defect>
**Validation:** <library> at <boundary>
**Data:** Firestore via <adapter or repository>; indexes in <file>
**Auth:** <token check>; roles and permissions in <path>
**Tests:** <runner> in <path>; <what is faked>
**Git:** base `<branch>`; branch `<pattern>`; commit `<format>` (enforced by <tool>); MR template `<path>`, target `<branch>`; tickets: <GitLab issues in `<host>/<group>/<project>` via glab (often a tracker project, not this code project) | other>
**CI/CD:** <provider and files>; environments <list>
**On edit:** format `<cmd with {file}>`; lint `<cmd with {file}>`; files `<.ext .ext>` | none
**On stop:** `<gates command>` | none
**Protected branches:** `<branch>`, `<prefix>-*`
**Watch out:** <three to five facts a newcomer would get wrong>
<!-- backend-dev:profile:end -->
```

Keep it under 25 lines: it is read in every session. Three lines drive more than the skills, so keep their shape exactly: **On edit** is read by the edit hook (after Claude edits a file it runs `format` then `lint` on it from the repo root, `{file}` being its path; lint errors go back to Claude; `none` turns it off), **On stop** by the stop hook (when Claude ends a turn in which it edited a file other than Markdown, it runs the command from the repo root; a failure goes back to Claude once per turn; `none` turns it off, and it is off until a lead turns it on, because the whole suite then runs at the end of every such turn), and **Protected branches** is what `kit-setup` turns into the deny rules below (exact names, plus `prefix-*` for a family of environment branches).

## Guard rules

`kit-setup` writes rules into the repo's `.claude/settings.json` under `permissions.deny` and `permissions.ask`, generated by `node ${CLAUDE_PLUGIN_ROOT}/scripts/guard-rules.mjs <protected branch | prefix-*>...` from the **Protected branches** line. The harness enforces them on Claude's tool calls. They block: pushes to a protected branch in every spelling seen in real sessions (`origin dev`, `HEAD:main`, `:dev`, `refs/heads/main`, `git -C … push`, behind `cd … &&`), `--no-verify` on commit or push, force pushes (`--force`, `-f`, `+ref`), `--all` and `--mirror`, AI attribution in a commit message, and the Read and Edit tools on `.dev.vars`, `.env` and `.env.local`. The Read deny also stops `cat`, `grep`, `head` and `cp` on those files (checked in real sessions); a script that opens one (`node -e "…readFileSync('.dev.vars')…"`) is not seen as a read, so the `ask` rules make a person approve any shell command that names `.dev.vars` or `.env`, samples included.

`--force-with-lease` on a feature branch stays allowed, and so does a look-alike branch such as `feat/dev` or `feat/prod-x`: a family `prod-*` blocks only branches that start with `prod-`. A push that names no branch (`git push`, `git push origin`, `git push -u origin`) is denied too: its target comes from git config, which no rule can see, so it could reach a protected branch; name the branch. Not covered, by design: `git push origin HEAD` while standing on a protected branch, and a target built from a shell variable. The server's branch protection and the repo's push hook cover those, and every rule binds only Claude, not a person at a terminal.

## Defaults for a project made from this kit's template

Used when a repo has no profile block, and written into `CLAUDE.md` by the scaffold.

| Field | Template value |
|---|---|
| Repo | single app; API in `src/` |
| Commands | install `npm install`; dev `npm run dev`; gates `npm run typecheck && npm test && npm run check` (`check` is `wrangler deploy --dry-run`); deploy `npm run deploy:<env>` |
| Layering | `routes.ts` → `controllers/` → `services/` (Effect programs) → `@/core` `Firestore` tag; modules in `src/modules/<plural>/`, registered in `src/modules/index.ts` |
| Errors | tagged errors (`core/errors.ts`) mapped once in `toErrorResponse`; a `throw` inside a service is a defect (bare 500) |
| Validation | Effect Schema: body decoded in the service, query and path through `validate()` |
| Data | Firestore REST adapter `core/firestore.ts`; indexes in `firestore.indexes.json` |
| Auth | Firebase ID token in `authMiddleware`; role from the `role` claim; ownership in the service |
| Tests | vitest; `makeFakeFirestore()` for services, `testApp()` for routes |
| Git | base `main`; `feat/<slug>`; conventional commits; pull request to `main` |
| CI/CD | GitHub Actions; envs `dev`, `stag`, `prod` in `wrangler.toml` |
| On edit | none: the template has no formatter or linter; `npm run typecheck` runs in the gates |
| On stop | none; to turn it on, `npm run typecheck && npm test` |
| Protected branches | `main` |
