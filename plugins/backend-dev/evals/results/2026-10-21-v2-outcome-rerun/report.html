**Cursor rules**
- The cursor is base64url of the last row's raw order-by values plus its document name. The adapter copies raw `timestampValue`s, so microsecond timestamps round-trip.
- **Gap to fix:** today the only check is `values.length === order.length`. A cursor from the createdAt-desc query is accepted by the from-asc query, and one from `ownerId=A` is accepted under `ownerId=B`. Both have 2 values, so the next page silently skips or repeats rows.
- **Fix:** encode `{f, v}`, where `f` is the first 12 characters of the SHA-256 of the canonical JSON of the filters, their values and the order directions. `limit` is excluded from `f`.
- A mismatched fingerprint or an unparseable cursor returns `400 Invalid cursor`.
- Cursors already in flight at deploy become invalid once.
- A cursor is not a snapshot. Rows inserted before the position are not returned. `from` can be edited while a request is pending, so a row can move between pages.
- History and balances have no cursor. History is at most 3 rows per request.

**Not queryable as asked**
- `status` together with `ownerId`: return 400. Supporting it needs two more composites, `(ownerId, status, createdAt desc)` and `(ownerId, status, from asc)`.
- Overlap ranges (requests that start before the range but run into it): not offered. The range filters on `from`, as it does today.
- A non-admin passing `ownerId` or `status`: ignored, as `status` is today.

## Consistency

The existing `decide` and `cancel` are `get` followed by an unconditioned `update`. Two approvals, or an approve racing a reject, both succeed today. The edit path has the same hole: an edit can land after an approve and change `from`, `to` and `type` under a snapshot. All three need preconditions.

**Mechanism:** one atomic `:commit` where every document that was read carries `currentDocument.updateTime`.
- **Approve:** the writes are the request update, the balance update and a history create (`exists=false`).
- **Cancel an approved request:** the same three writes.
- **Cancel a pending request, or reject:** request update plus history create.
- **Entitlement change:** balance update, checked so `entitled ≥ used`.
- **Balance creation:** create with `exists=false`.

If any precondition fails, nothing is written. I chose this over `:beginTransaction` because every document read is also preconditioned. It takes one round trip instead of begin, batchGet and commit, it has no lock waits, and the invariant still holds. A transaction would be a drop-in alternative.

**Race example:** 5 days remain and requests A and B need 3 each. Both read the balance at revision U1. A commits and the balance moves to U2. B's commit fails on the stale precondition and writes nothing. B re-reads, sees 3 used + 3 > 5, and gets 409 "insufficient balance".

**Loser behaviour**
- Firestore returns HTTP 400 with `error.status = FAILED_PRECONDITION`, or 409 for ABORTED or ALREADY_EXISTS. The adapter must read the body status, not the HTTP code. Today `invalidCursor` would turn any 400 into "Invalid cursor".
- The service retries up to 3 times with 20–100 ms jitter. Each attempt re-reads and re-validates.
- A deterministic loser gets 409 right away: request no longer pending, or insufficient balance.
- If retries run out, the loser gets 409 "concurrent update, retry", and the client retries.
- I did not use `increment` (no condition, so the balance could go negative) or sharding (volume is far below 1 write/s).

**What the adapter must gain (implementation work):**
1. `Doc` must expose Firestore's raw `updateTime`, for example as `revision`. The app's `updatedAt` is a millisecond value and can't serve as a precondition.
2. A `commit(writes[])` method on the `Firestore` tag. Each write is an update with a mask or a create, with a precondition of `updateTime` or `exists`. It sets `updatedAt` and `createdAt` itself, and maps the precondition and abort errors to a retryable tagged error added in `errors.ts` and `run.ts`.
3. An optional `revision` precondition on `update`, for the edit path.
4. The fake must give each document a revision counter and make `commit` all-or-nothing. That lets tests force a stale revision to simulate two admins.
5. The cursor fingerprint described above.

4. **Deploy code with `LEAVE_BALANCE_ENFORCE=off`:**
   - Readers tolerate absent `deductedDays`, `balanceId` and `schemaVersion`.
   - Decide, cancel and edit use preconditions. With the flag off they behave as today, except that they also write the history event and the `deductedDays` snapshot, and they never touch balances.
5. **Backfill requests:**
   - Run it from a local script with the service account. It is idempotent: skip documents with `schemaVersion ≥ 2`.
   - Each patch uses an `updateMask` of `deductedDays`, `balanceId` and `schemaVersion` only. It leaves `updatedAt` alone, and it carries the read's `updateTime` as a precondition.
   - Approved requests in the seeded years of a tracked type get the day count and `balanceId`. All others get null.
6. **Backfill history:** one event per legacy approved or rejected request, with id `{requestId}_{status}`, `actorId = decidedBy`, `createdAt = decidedAt`, `source: "backfill"` and an empty comment. Create it with `exists=false` so reruns skip. Legacy cancellations get no event, because the actor was never recorded.
7. **Seed balances** from the HR sheet of entitlements, using `exists=false`.
   - `usedDays` is the sum of `deductedDays` over approved requests for that year and type.
   - If the sum exceeds the entitlement, skip that balance and report it to HR. Do not auto-create a balance that violates the invariant.
8. **Flip** `LEAVE_BALANCE_ENFORCE=on`, then run reconcile at once.
   - Reconcile recomputes `used` from the requests and reports drift. It fixes drift only with a preconditioned write, and only when the result is still ≤ entitled.
   - The drift window is approvals made between the seed read and the flip.
   - Then run reconcile on a schedule, daily or weekly.
9. **Rollback:** `wrangler rollback`, or redeploy with the flag off. The fields are additive and old code ignores them.
   - Run reconcile before re-enabling.
   - Two things break rollback: an unmasked PATCH (it would wipe the new fields) and a strict decoder meeting a new enum value. I add no status values, and the adapter always masks.

## Cursor rules
The existing keyset cursor (order values plus `__name__`, `limit+1` lookahead) is sound. It has one gap: it checks only the array length. A cursor from a different filter set of the same shape silently returns wrong rows.

1. **Envelope.** `{v:1, h, k:[…values, name]}`, base64url. `h` is a truncated SHA-256 of the collection, the filters (field, op, value) and the order-by. A mismatch returns 400 "cursor does not match this query".
2. **Security.** The hash is not a secret. Security comes from the server-forced `ownerId` filter, which is part of `h`. A cursor from one user is rejected for another.
3. **Type check.** Values are checked against the order fields (timestamps for `from`, `createdAt` and `at`), and the last value must be a document path under the same collection. Otherwise 400.
4. **Tie-break.** `__name__` is always last, in the same direction as the last order field. There are no skips or duplicates on ties.
5. **What may change between pages.** `limit` may change. Filters and range may not, because the hash differs. Adding or removing a date range switches the order from `createdAt desc` to `from asc`, so the client must restart from page one.
6. **Next cursor.** One is returned only when more rows exist.
7. **Lifetime.** Cursors don't expire and a deleted last row is fine. Pages are not a snapshot, so a status change mid-pagination can make a row appear or vanish from a status-filtered list. There are no total counts.
8. **Compatibility.** Accept the old bare-array cursor for one release, then drop it.

## Concurrency
Today `decide` and `cancel` read, check, then write with no guard, so two admins can both approve one request. The adapter has no transactions, so add them. I'd use Firestore REST `beginTransaction`, then reads with `?transaction=` or `batchGet`, then one atomic `commit` that carries the writes. I'd not use `updateTime` preconditions, because `Doc` exposes only a millisecond `Date` while Firestore's `updateTime` has microsecond precision.

Add `db.transact(fn)` to the `Firestore` tag. It retries the whole function on 409 `ABORTED`, up to 5 times with jitter, then fails with a retryable error. The fake Firestore needs the same semantics: a version check at commit.

**Approve**, inside one transaction:
1. Read the request and the balance.
2. Require `status == pending`.
3. For tracked types, require the balance doc to exist (409 if it doesn't) and `used + days ≤ entitled`. If not, return 409 with the remaining days.
4. Commit atomically:
   - the request update (`status`, `decidedBy`, `decidedAt`, `deductedDays`);
   - the balance update (`used`);
   - a create-only history event.

**Cancel an approved request.** Check that `from` is still in the future, using the server clock inside the transaction. Then set `used -= deductedDays`, clear `deductedDays`, set the status, and write the history event. If `used` would go below 0, fail loudly and log it. That means the data is corrupt.

**Reject and cancel of a pending request.** These also go through a transaction, so the status race is closed. They write the request plus the history event and don't touch the balance.

The balance doc is part of every approval's read set. Two concurrent approvals for the same employee, type and year conflict, and the loser re-reads the new `used`. Approvals for different balances don't contend.

I didn't use `FieldTransform.increment`. It can't enforce the `used ≤ entitled` guard without a read.

A scheduled reconcile job recomputes `used` as the sum of `deductedDays` over approved requests per balance. It reports mismatches and doesn't fix them silently. It's a safety net, not the enforcement.
