**Consumers:** unknown. The repo can't tell me who calls `/api/v1/timeOffRequests/*`, so I treat them as existing clients that must keep working and keep every change additive. ## Consistency
**Approve** runs in a transaction. The steps are:
1. `:beginTransaction` (read-write).
2. `:batchGet` the request inside the transaction.
3. Check `pending`, then compute `deductions` from `from`/`to` (inclusive calendar days, split by year, at most two entries).
4. `:batchGet` those balance docs inside the same transaction.
5. Check `usedDays + days ≤ entitledDays` for each.
6. `:commit` four writes together: the request (masked, `exists=true`), each balance's `usedDays` (masked), and the history row (`exists=false`).

**Cancel and reject** go through the same transaction helper. Cancel refunds only when the request is `approved` as read inside the transaction. It refunds from the stored `deductions`, not a recomputation. If `usedDays − days < 0`, it fails with a 500 and a log line instead of clamping, because clamping hides drift.

**Why cancel can't be a plain read-then-update.** Cancel reads `pending`, an approve commits and deducts, then cancel writes `cancelled` with no refund. That leaks balance. It is a real race in today's `cancelTimeOffRequest`. A cancel of a pending request must use the transaction too.

**Editing a pending request** needs `currentDocument.updateTime` from its read. Otherwise an edit that raced an approve can change the dates of an already-deducted request.

**Losers**
- **Insufficient or missing balance:** `409 Conflict`. It is deterministic, so there is no retry.
- **Request no longer pending:** `409 Conflict`, as today. The client re-reads.
- **Commit `ABORTED`** (another transaction on the same balance): the service retries in a new transaction, 3–5 attempts with jitter. The `now` and history id are fixed before the first attempt. After that it returns `503` with `Retry-After`. The client may retry.
- **Failures before commit:** call `:rollback` best-effort so locks are released.

Contention per employee balance is far below one write per second, so no sharding.

**What the adapter lacks** (implement work; the tag and the fake both need it):
1. `create` with a caller-supplied id and `exists=false`, for balance and history ids.
2. A transaction primitive: begin, get inside the transaction, commit with multi-document writes and preconditions, rollback.
3. `Doc.updateTime` and an `ifUpdateTime` option on `update`.
4. A `FirestoreError` that carries the gRPC status string. `ABORTED` and `ALREADY_EXISTS` are both HTTP 409 and are indistinguishable today.
5. The cursor v2 format above.

## Cursor rules

1. The default order is `createdAt desc`, which is immutable. A ranged query orders by `from asc`.
2. `__name__` is always the final sort key, in the same direction as the last field. The adapter already does this, and it fetches `limit+1` to detect a next page.
3. Never filter in memory after the query. Every page except the last is full, and that is also why overlap ranges are out.
4. Bind the cursor to the query. Today a cursor from one filter can be replayed on another, and a wrongly-typed one only fails when Firestore returns a 400. Encode `[v1, hash(collection, effective where, orderBy), ...values, name]`, and return 400 on a hash mismatch.
   - "Effective where" includes the forced `ownerId` for non-admins.
   - This is a correctness fix. Filters are server-applied, so a forged cursor can't widen access.
5. Cursors in flight at deploy become invalid. Clients get 400 `Invalid cursor` and restart, which is acceptable.
6. Sort fields come only from the server allowlist, never from the caller.
7. `from` can change while a request is pending, so a concurrent edit can duplicate or skip a row in a `from`-ordered scan. That is acceptable, and I'd document it.
8. History and balances order by `__name__` alone. The zero-padded version in the ID makes that chronological.

## Concurrency

**Adapter change.** Add `commit(writes[])`, which POSTs to `:commit`:
- Each write carries `currentDocument.updateTime` for an existing document, or `exists:false` for a new one.
- A commit is all-or-nothing, so the preconditions are checked atomically.
- `toDoc` must expose the raw `updateTime` string. Don't parse it into a `Date`, because millisecond truncation breaks the precondition.
- Strip it from API output.
- `fake-firestore` needs the same semantics.

**Approve** runs this loop:
1. Read the request. It must be `pending`.
2. If the type isn't `unpaid`, read the balance. If `used + days > granted`, or the balance is missing, return 409 `insufficient balance`.
3. Commit four writes:
   - the request: `status`, `decidedBy`, `decidedAt`, `chargedDays`, `version+1`
   - the balance: `used+days`, `version+1`
   - the history event
   - the ledger entry
4. The request and balance writes both carry their `updateTime` preconditions.
5. On `FAILED_PRECONDITION` (400) or `ABORTED` (409), re-read and retry. Use up to 5 attempts with jitter, then return 409 "try again".

**Why this is safe.** Take a balance of 5 and two 3-day approvals for the same employee. Both read `used=0`. The first commit wins. The second fails its precondition on the balance, re-reads `used=3`, and gets 409. An approve racing a cancel or an edit of the same request fails the same way on the request document.

**Cancel of an approved request** goes through the same loop and refunds `chargedDays`. If `used < chargedDays` or the balance is missing, fail with a 500. Never clamp.

**Existing paths must move to the same helper.** `updateTimeOffRequest`, `cancelTimeOffRequest` and `create` currently check the status and then write. An edit can land after an approval, and a cancel can't refund.

**Why preconditions rather than `beginTransaction`:** no locks are held across Worker subrequests, and the adapter change is smaller. Per-employee-and-type write rates are tiny.

Firestore has no CHECK constraint, and the service account bypasses security rules. The guarantee comes from read-then-precondition-commit, plus a reconciliation check. Deny client SDK access to these collections anyway.

- A manager can still approve dates they viewed before the employee edited them. Closing that means the client sends the `updatedAt` it saw, which is a contract change, so it is left out of this design.
- A manager approving their own request is rejected.
- A non-reportee gets 404, matching the existing "no enumeration" rule.

**Data leaving the system**
- **Employee email:** contains type, dates, decision and approver email only. It does not include the free-text `reason`.

## ADR 0001 — Queue and cron for decision emails and the monthly export, with Firestore preconditions on decisions

Status: proposed. Date: 2026-10-21.

**Context**
- Employees need an email on each approve or reject, and HR needs last month's CSV on the 1st.
- Both are side effects to other systems: an email provider and R2. They can fail and must not be lost or duplicated.
- The worker has no queue, cron or mailer today.
- `decide()` has a race: two concurrent approvals both succeed, and a trigger attached to that write would inherit the race.
- Volumes are small: roughly hundreds of decisions a month and about 2 000 export rows, so the cost is in correctness rather than throughput.

**Decision**
- **Decision writes:** `decide`, edit and cancel gain a Firestore `updateTime` precondition.
- **Notice flag:** the decision write also sets `noticePending` and `noticeKind` on the same document, which is the outbox.
- **Emails:** a Cloudflare Queue `leave-jobs` (with a dead-letter queue) carries the id-only messages. The consumer sends the email with idempotency key `notice:${requestId}:${noticeKind}` and clears `noticePending`.
- **Sweep:** an hourly cron re-enqueues notices still pending after 15 minutes, which covers a lost enqueue.
- **Export:** a monthly cron enqueues `export:${YYYY-MM}`. The consumer snapshots the CSV to R2, creates `exports/{YYYY-MM}` with the not-exists precondition, emails HR with that key, and sets `emailedAt`.
- **Scope line:** this amends any "no Queues" line in `architecture.md`.

**Alternatives considered**
- `ctx.waitUntil` for the email — the work is lost if the isolate is evicted, and there is no retry or dead letter.
- Sending the email inside the request — a provider outage would fail an approval that has already been decided, and it adds latency.
- A 5-minute polling cron as the only mechanism — it costs reads every tick with no backoff or dead letter, and it delays emails up to 5 minutes. A bounded hourly sweep is kept only as a safety net.
- A Durable Object per request for ordering — there is no hot key, and a Firestore precondition already settles the race.
- A Firestore transaction (`beginTransaction` and `commit`) for decide — it costs extra subrequests for the same guarantee as `updateTime`.
- Cloudflare Workflows for the export — it brings a new primitive for a four-step job whose steps are each idempotent already.
- Querying Firebase Auth for the employee's email at send time — it needs another OAuth scope and adds a dependency that can fail.

**Consequences**
- **Easier:** approvals no longer depend on the mail provider. Retries are safe, and the HR file is a reproducible snapshot.
- **Harder or costlier:**
  - It needs the Workers Paid plan and a queue and an R2 bucket in each of the 3 envs.
  - `index.ts` gains `scheduled` and `queue` handlers, and the `Firestore` tag gains two operations.
  - The create contract changes, because a token without an email is now rejected.
  - Delivery is at-least-once, so a provider that ignores the idempotency header can send a duplicate.
- **Monitor:**
  - Dead-letter queue depth above 0 should alert.
  - Sweep finds above 0 should warn, because they mean enqueues are failing.
  - `exports/{prev month}` with no `emailedAt` by 03:00 UTC on the 1st should alert.
  - A rise in decide Conflict responses would show a double-click or UI bug.
- **Revisit if:**
  - Volume reaches many thousands of decisions a day, which would call for per-message batching changes.
  - HR wants per-team or time-zone-based months.
  - The provider offers no idempotency key.
  - Cloudflare Workflows becomes the house pattern for multi-step jobs.

## Request path vs background

**Request path (approve/reject):**
1. The caller must be the request's `approverId`. An admin override is possible. The approver is never the owner.
2. One Firestore `:commit` does two things atomically:
   - Update the request with `status`, `decidedBy` and `decidedAt`, under an `updateTime` precondition.
   - Create `emailOutbox/decision:{requestId}` with `exists=false`.
3. Respond 200. No email I/O happens inline.
4. Optionally call `ctx.waitUntil(deliver(id))` as a fast path.

**Background:**
- `*/5 * * * *` is the sweeper. It delivers due outbox rows and advances the HR export.
- `0 1 1 * *` seeds `exports/{YYYY-MM}` for the previous month. It only creates the job doc, and the sweeper does the work. That gives one retry mechanism for both features.

`waitUntil` is only a latency optimization. It gets about 30 seconds after the response and isn't durable. The outbox row is the real guarantee.

## Retry safety

**Decision emails (at-least-once delivery, made effectively once):**
- **No double decision:** the outbox doc id is deterministic, and the `updateTime` precondition also catches a decide racing a cancel. A second decider gets 409 instead of a second email.
- **Delivery states:** rows go `pending` → `sending` → `sent`, or `dead`.
- **Claim:** a compare-and-set sets `leaseUntil` (about 2 minutes), so the fast path and the sweeper can't both send. An expired lease is retaken.
- **Provider dedupe:** the send passes `Idempotency-Key: decision:{requestId}`. A crash between "provider accepted" and "marked sent" is then deduplicated, provided the provider supports it. Resend does for about 24 hours, but check that for whichever provider is chosen.
- **Backoff:** 4xx permanent errors go straight to `dead`. 429, 5xx and network errors retry with exponential backoff, capped inside the provider's dedupe window. Beyond that, a rare duplicate is the accepted failure mode.
- **Payload:** the row stores a snapshot of recipient, decision and dates, so a later cancel or edit doesn't change what was announced.

**HR export:**
- **Period:** it comes from `event.scheduledTime`, never `Date.now()`, so a late or re-run tick targets the same month.
- **Job doc:** `exports/2026-09` is created with `exists=false`. A second cron fire or a retry hits 409 and resumes.
- **Steps:** claim lease → query → build CSV → R2 put → mark `built` → send with `Idempotency-Key: hr-export:2026-09` → mark `sent`.
- **Resume:** once the job is `built`, retries reuse the stored file and only re-send. The file HR gets is stable even if requests are cancelled later.
- **Query:** `status == approved` and `from ∈ [monthStart − MAX_SPAN_DAYS, monthEnd)`, then filter `to ≥ monthStart` in memory. `MAX_SPAN_DAYS = 30` bounds this, and the existing `status+from` index serves it. Paging goes through the adapter's cursor.
- **CSV safety:** quote per RFC 4180. Prefix any cell starting with `= + - @` with `'` (formula injection), since `reason` is free text. I'd leave `reason` out by default, because sick-leave reasons are sensitive.

# ADR-0001: Leave approval notifications and monthly HR export

**Status:** Proposed (2026-10-21)

**Context.** The Worker API (Hono + Effect + Firestore REST) already has time-off CRUD and an admin-only approve/reject. The new requirements are:
- Manager-based approval.
- An email to the employee on every decision.
- A CSV of last month's leave sent to HR on the 1st.

Workers have no transactions across Firestore and an email provider, and cron triggers and `waitUntil` give no exactly-once guarantee. The current decide path is read-then-write and racy.

**Decision.**
1. **Approver.** `approverId` (from `employees/{uid}.managerId`) is snapshotted on the request at creation. Only the approver, or an admin, may decide. The owner may never decide their own request.
2. **Atomic decision.** Decide is a single Firestore `:commit`. It updates the request under an `updateTime` precondition and creates `emailOutbox/decision:{requestId}` with `exists=false`. The adapter gains `commit`, `updateTime` exposure and precondition-failure → `Conflict` mapping.
3. **Transactional outbox, delivered by a cron sweeper (`*/5`).** An optional `waitUntil` fast path exists. Delivery uses a lease, exponential backoff and a dead state. The provider `Idempotency-Key` equals the outbox id. We accept at-least-once delivery with provider-level dedupe.
4. **HR export is a job doc.** A monthly cron seeds `exports/{YYYY-MM}`, and the same sweeper completes it through resumable, idempotent steps. The period comes from `scheduledTime`. The CSV is stored in R2 and emailed with a deterministic idempotency key.
5. **Mail stays off the request path.** Mailing lives behind an Effect `Mailer` tag used only by jobs. `Run` stays `Firestore`-only, and `index.ts` exports `{ fetch, scheduled }`.
6. **Per-env crons and recipients.** Dev and stag send only to test inboxes.

**Alternatives considered.**
- **Send inline in the request:** couples approve/reject availability and latency to the mail provider, and a failure after commit loses the email.
- **`waitUntil` only:** not durable.
- **Cloudflare Queues:** gives retries and a DLQ, but there is still a dual-write problem between Firestore and the queue, so an outbox is needed anyway. It is a reasonable later upgrade if volume grows.
- **Delivery state on the request doc:** this avoids multi-doc commits, but it leaks internal fields into API responses and doesn't generalize to other emails.
- **A single `*/5` cron that also seeds the export:** self-heals a missed monthly tick. Rejected for now as less legible.

**Consequences.**
- Decisions are race-safe and an email is never lost once the decision commits. Delivery latency is a few seconds on the fast path and up to 5 minutes otherwise.
- A rare duplicate email is possible if retries outlive the provider's dedupe window.
- New surface to build and maintain: the commit/precondition adapter work, an `employees` data source, an R2 binding, email secrets, new indexes and per-env cron config.
- A missed monthly cron seed has no alerting yet. A follow-up should add a dead-letter or "export not sent by the 2nd" alert.

**Open items.** Email provider, source of the manager relationship, CSV semantics, and R2 approval. See the questions above.
