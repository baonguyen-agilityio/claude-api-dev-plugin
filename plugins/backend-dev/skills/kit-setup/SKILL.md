Set up this repository for the backend-dev kit. App path hint from the user: "$ARGUMENTS" (empty means find it).

The profile format and the template defaults are in `${CLAUDE_PLUGIN_ROOT}/references/project-profile.md`. Read it first.

Work only from evidence in this repo. Every field you cannot establish from a file stays `?: <question for the lead>`. Never invent a command, a branch name or a tool. Never open `.dev.vars`, `.env` or `.env.local`: the deny and ask rules this skill writes are not in force yet, and their samples (`.dev.vars.example`, `.env.example`) carry every key name you need.

1. **Locate the repo and the API.** `git rev-parse --show-toplevel`; package manager from the lockfile; workspaces (`pnpm-workspace.yaml`, `workspaces` in `package.json`, `turbo.json`); the API app is the package that depends on `hono` and has a `wrangler.toml`. More than one candidate and no hint: list them and ask which.
2. **Commands.** From the root and app `package.json` scripts: install, dev, lint or typecheck, test (scoped to the app when the repo is a monorepo), build or `wrangler deploy --dry-run`, deploy per env. Quote them exactly as a person would type them from the repo root. In a monorepo, check how the API app consumes shared packages: when it imports them from their built output (`main` or `exports` pointing at `dist/`), the gates start with that build (`pnpm --filter <shared> build` or the turbo build that includes it), otherwise the app's tests run against stale code.
3. **Layering and style.** Open one representative module end to end (route, controller, service, schema, tests) and the shared package if there is one. Record where a new endpoint's pieces go, how failures are raised (tagged errors, thrown exceptions, `Result` values) and where they become a status, which validation library is used at which boundary, how Firestore is reached (adapter, repository base class), where roles and permissions are checked, and what tests fake.
4. **Git and tickets.** Base and default branches (`git branch -r`, CI triggers); branch names from `git log --format=%D` and recent merges; commit format from `commitlint.config.*`, `.husky/commit-msg` and the last 20 subjects; MR or PR template paths (`.gitlab/merge_request_templates/`, `.github/pull_request_template.md`); the ticket system from the commit format and templates (`[#123]` and `Closes #123` mean GitLab or GitHub issues). **Find the project that holds the tickets**, which is often not the code project: take two ids from recent commit subjects, or from merged MR titles (`glab mr list --merged`, run from the repo root with no `cd` so glab takes the host from the remote) when the clone is shallow, skipping placeholders such as `#000`, and look them up across the instance, `glab api --hostname <host> "issues?scope=all&iids[]=<id>"`; record the project they belong to as `<host>/<group>/<project>`. If the code project has no issues at all and nothing is found, write `?: which project holds the tickets`.
5. **CI/CD and environments.** Workflow files (`.gitlab-ci.yml`, `.github/workflows/`), the env blocks in `wrangler.toml`, deploy scripts. **Protected branches** for the guard rules: the base and default branches, every branch a deploy workflow or MR template targets, and the server's own list when readable (`glab api --hostname <host> "projects/<url-encoded path>/protected_branches"`, `gh api repos/<owner>/<repo>/branches?protected=true`); then every environment branch, since deploys often run from branches no workflow file names: list the remote's branches (`git ls-remote --heads origin`) and add each one named after an environment (`dev`, `stag`, `staging`, `prod`, `production`, `main`, `master`, `release`, and the environment names in `wrangler.toml` and CI), and for each of those names that also starts other branches with a hyphen (`prod-eu`, `prod-eu-job`), the family as `prod-*`. A family covers every branch that starts with the prefix, so list it in the summary for the lead to check: a work branch named that way (`dev-coverage`) is blocked too. Never a bare `*`.
6. **On edit.** The per-file commands the edit hook runs, from the repo's own tools only: a formatter whose config and dependency both exist (`.prettierrc*` and `prettier` → format `<pm> exec prettier --write {file}`), a linter likewise (`eslint.config.*` and `eslint` → lint `<pm> exec eslint --max-warnings=0 {file}`, reusing the flags `lint-staged` passes if it lists any), and the file types from the `lint-staged` globs, else `.ts .tsx .js .jsx .mjs .cjs .json`. Commands run from the repo root, so use the package manager's root form. Neither tool present: `**On edit:** none`. **On stop** is `none`: running the gates at the end of every turn that edited code is the lead's call, so say in the summary how to turn it on (the gate command from step 2, or a faster part of it, in backticks) and that the base branch should be green first.
7. **Watch out.** Three to five facts a newcomer would get wrong, each quoted from a file, never inferred. For git hooks, open each hook file (`.husky/pre-commit`, `.husky/pre-push`, `.husky/commit-msg`, `.pre-commit-config.yaml`) and say what each one runs. Examples: versions that disagree (README vs `.node-version` vs CI), a dev setup that writes to shared data, a README that is a stub, a hook that runs slow checks on push.
8. **Write the block** between `<!-- backend-dev:profile:start -->` and `<!-- backend-dev:profile:end -->` in the repo-root `CLAUDE.md`: replace an existing block, otherwise append; never touch anything outside the markers; create the file if it does not exist. Under 25 lines, with the **On edit**, **On stop** and **Protected branches** lines in the reference's exact shape (the hooks parse them).
9. **Settings.** In `.claude/settings.json` (create if absent, merge if present, keep every existing key): set `attribution.commit` and `attribution.pr` to `""` (the kit never adds AI attribution); add `permissions.allow` entries for the exact gate commands from step 2 (for example `Bash(pnpm --filter space test)`), nothing broader; add the guard rules: run `node ${CLAUDE_PLUGIN_ROOT}/scripts/guard-rules.mjs <every protected branch from the profile>` and add its `deny` list to `permissions.deny` and its `ask` list to `permissions.ask`, as printed, never hand-written or abbreviated (deny blocks pushes to those branches, `--no-verify`, force pushes, attribution, and the Read and Edit tools on secret files; ask makes a person approve any other shell command that names a secret file). Keep existing entries. Change no other keys. Claude Code asks before writing this file; if the write is declined, print the JSON for the lead under Questions and go on.
10. **Ignore files and worktrees.** Check with `git check-ignore -v .claude/checkpoints/x .claude/settings.local.json .claude/worktrees/x .claude/settings.json`. Add the first three to `.gitignore` only when nothing ignores them yet. Write `.worktreeinclude` at the repo root listing each local secret file the app reads that git ignores and whose sample exists (`<app path>/.dev.vars` for `.dev.vars.example`, likewise `.env.local`), one path per line, each confirmed ignored with `git check-ignore` first (a tracked file must not be listed), so Claude Code copies them into a new worktree (`claude -w`) without anyone opening them; keep existing lines. If an existing rule also ignores `.claude/settings.json` (a bare `.claude` line), the team cannot commit its settings: do not rewrite the rule, list it under Questions with the fix (`.claude/*` plus `!.claude/settings.json`).
11. **Report and stop.** Do not commit. Show:

```markdown
## Kit setup: <repo>
**Written:** CLAUDE.md profile block (new | refreshed), .claude/settings.json (keys added), .gitignore (lines added), .worktreeinclude (paths)
**Hooks and guards:** on edit <format and lint commands | none>; on stop none (how to turn it on); deny rules for <protected branches>
**Profile:** <the block, verbatim>
**Questions for the lead:** <every ?: field, one line each, with where you looked>
**Next:** review the diff (`git diff`), answer the questions in the block, commit as one change in the repo's commit format.
```
